# Данные, модель и добавление новых сур

Обновлено: 19 октября 2026 года.

## Нужны ли записи для новой суры

Ответ зависит от цели.

| Цель | Нужны записи до реализации? | Что требуется |
|---|---:|---|
| Показать текст новой суры | Нет | Номер, название, аяты |
| Дать прослушать аяты | Нет собственных записей | Аудио из Quran API или лицензированный источник |
| Получить черновую ASR-подсветку | Нет | Текст суры, выбор суры в API и интерфейсе |
| Утверждать, что ошибки находятся надёжно | Да | Записи разных людей и независимая учительская разметка |
| Дообучить модель под кораническое чтение | Да | Аудио + точная фактическая расшифровка + корректное разделение данных |
| Проверять таджвид/махрадж | Да, значительно больше | Фонемная и временная разметка специалистами; текущего Whisper недостаточно |

Предобученная Whisper уже знает арабскую речь в общем виде. Ей не нужна одна «эталонная запись» каждой суры, чтобы попытаться её распознать. Канонический текст нужен алгоритму сравнения после распознавания, а эталонное аудио нужно пользователю для прослушивания.

Записи нужны для измерения реального качества. Без них новая сура будет работать технически, но неизвестно, сколько подсветок вызвано ошибками ученика, а сколько — ошибками ASR.

## Почему нельзя обучать только по названию суры

Если ученик должен был прочитать «Аль-Фаляк», это не означает, что он фактически произнёс канонический текст. Он мог пропустить, заменить или повторить слово. Если во время обучения присвоить такой записи идеальный текст, модель научится исправлять речь в ожидаемую суру и скрывать именно те ошибки, которые проект должен находить.

Для каждой обучающей записи нужна дословная расшифровка того, что реально слышно. Для продуктовой оценки дополнительно нужна разметка:

- что было пропущено;
- что заменено;
- что повторено;
- где вступление, пауза и конец чтения;
- уверен ли преподаватель в разметке;
- есть ли проблема произношения, которую пословный ASR не способен оценить.

## Текущая реализация каталога

По состоянию на 19 октября 2026 года ограничение одной сурой снято:

- frontend загружает список всех 114 сур и Uthmani-текст через Quran API;
- пользователь выбирает начало и конец диапазона, не более 10 аятов за попытку;
- номер суры и диапазон передаются в локальный AI API;
- `ai-service/quran_catalog.py` проверяет параметры, получает канонический текст серверной стороной и кэширует его в памяти;
- сравнение и live-tracking принимают выбранный текст параметром, а не используют глобальную 112-ю суру;
- басмала, которую одно из зеркал API добавляет внутрь первого аята, нормализуется одинаково на клиенте и сервере.

Встроенный текст «Аль-Ихляс» сохранён как offline-fallback и для совместимости старых CLI-тестов. Для других сур во время локальной демонстрации требуется интернет. Поддержка всех сур означает техническую доступность, а не доказанную точность: реальными записями пока проверялась только 112-я сура.

## Реализация каталога

Минимальная серверная структура:

```python
SURAHS = {
    112: {
        "name_ru": "Аль-Ихляс",
        "name_ar": "الإخلاص",
        "ayahs": [...],
    },
    113: {...},
}
```

API принимает `surah`, `ayah_from`, `ayah_to`, проверяет диапазон и выбирает соответствующий текст только в слое сравнения. Сырой `Recognizer.transcribe()` остаётся независимым от выбранной суры.

Frontend получает каталог из Quran API. `useAyahAudio` принимает номер суры и держит отдельный кэш аудио для каждой загруженной суры.

## Порядок добавления

1. Собрать 10–20 записей для smoke-проверки 113 «Аль-Фаляк» на разных голосах и устройствах.
2. Аналогично проверить 114 «Ан-Нас».
3. Проверить 1 «Аль-Фатиха» отдельным этапом: она длиннее, чаще содержит варианты темпа и требует более строгой предметной проверки.
4. После этого постепенно добавлять проверочные записи для остальных сур, начиная с наиболее востребованных школой.

Новые суры лучше добавлять последовательно, потому что каждая увеличивает число сценариев, которые нужно проверять.

## Минимальный набор данных для MVP

Для демонстрации механики достаточно нескольких записей. Для заявления о качестве целевой план эксперимента остаётся таким:

- не менее 100 записей;
- 20–30 участников;
- несколько телефонов и помещений;
- правильные чтения и естественные ошибки;
- контрольная часть размечена двумя преподавателями;
- разделение train/dev/test по людям, а не по файлам одного человека;
- тестовый набор не используется для настройки порогов и выбора checkpoint.

Число 100 — план первого пилота, а не гарантия достаточности для полноценной модели. После первого замера объём уточняется по разбросу ошибок.

## Метаданные одной записи

Для каждого файла желательно хранить:

```json
{
  "recording_id": "uuid",
  "speaker_id": "pseudonymous-id",
  "surah": 112,
  "ayah_from": 1,
  "ayah_to": 4,
  "device_class": "phone",
  "environment": "quiet-room",
  "intended_text": "канонический текст задания",
  "verbatim_transcript": "что фактически произнесено",
  "teacher_errors": [],
  "annotators": 1,
  "consent_version": "v1",
  "split": "train|dev|test"
}
```

Имя и контакт участника не должны попадать в исследовательский manifest. Связь с реальным человеком, если она вообще нужна, хранится отдельно с ограниченным доступом.

## Как оценивать

Нужны как минимум два разных измерения:

1. ASR: WER/CER по дословной человеческой расшифровке.
2. Продуктовая задача: precision, recall и F1 локализации пропусков, замен и повторов относительно разметки преподавателя.

Расстояние расшифровки до канонического текста не заменяет ни одно из этих измерений. Оно смешивает ошибку ученика с ошибкой распознавания.

## Когда имеет смысл дообучение

Дообучение стоит начинать после появления размеченного train/dev набора и замера исходной модели. Сначала нужно понять повторяющиеся классы ошибок базового ASR. Затем адаптер сравнивается с исходной моделью на неизменном независимом test-наборе.

Если после обучения модель просто чаще восстанавливает канонический текст, но хуже сохраняет реальные ошибки ученика, для проекта это ухудшение, даже если строка визуально стала ближе к суре.
