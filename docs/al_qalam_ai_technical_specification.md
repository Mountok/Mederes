# Техническое задание: Al-Qalam AI

> Документ описывает целевую систему и исходный аудит сентября 2026 года. Актуальное состояние реализации зафиксировано в `START_HERE.md`; архитектурные уточнения — в `ARCHITECTURE.md`.

## 1. Общие сведения

### 1.1. Назначение документа

Документ определяет границы, архитектуру, требования, этапы разработки и критерии приёмки технологического модуля анализа чтения Корана, интегрируемого в существующий электронный журнал Al-Qalam.

### 1.2. Цель проекта

Создать проверяемую технологию, которая принимает запись чтения заранее выбранного аята, сопоставляет речь ученика с эталоном, обнаруживает основные ошибки заучивания и предоставляет преподавателю объяснимый предварительный результат.

### 1.3. Принцип продукта

Al-Qalam AI является помощником преподавателя, а не автономным судьёй правильности религиозного чтения. Любой результат алгоритма имеет статус предварительного до подтверждения преподавателем.

## 2. Результаты аудита текущего репозитория

### 2.1. Существующий стек

- frontend: React 19, Vite 8, React Router, Axios;
- backend: Go 1.25, Gin, sqlx;
- база данных: PostgreSQL с SQL-миграциями;
- авторизация: JWT, роли `teacher`, `staff`, `parent`, `student`;
- мультитенантность: данные разделяются по `school_id`;
- медиа и онлайн-занятия: LiveKit и WebSocket;
- модуль Корана: внешний API для списка сур, арабского текста, перевода и аудио;
- развёртывание: Go-сервис, статическая сборка frontend, PostgreSQL и LiveKit в Docker.

### 2.2. Сильные стороны основы

- понятное разделение handler → service → repository;
- существующие сущности школы, группы, ученика и урока;
- контроль доступа преподавателя и сотрудника к школам и группам;
- готовый личный кабинет ученика;
- существующий модуль Корана и воспроизведения аятов;
- готовая реальная площадка для пилота;
- возможность добавить AI-модуль без переписывания журнала.

### 2.3. Ограничения текущей версии

- локальная страница уже принимает аудио и микрофон, но отсутствует долговременное хранение пользовательского аудио в продукте;
- отсутствует очередь фоновых задач;
- существует локальный loopback-only Python ML-сервис для демонстрации, но отсутствуют production worker и реестр версий моделей;
- текст и аудио Корана зависят от внешнего API и не закреплены версией;
- отсутствует сущность задания на чтение;
- отсутствует экспертная разметка ошибок;
- добавлены тесты нормализации, выравнивания, распознавания, локального HTTP API и браузерного аудиозахвата; backend пока не имеет отдельных unit-тестов;
- настройки HTTP-сервера имеют `WriteTimeout` 15 секунд, поэтому ML-обработку нельзя выполнять синхронно внутри пользовательского запроса;
- пример конфигурации содержит небезопасные dev-значения, которые нельзя использовать в production;
- открытые маршруты LiveKit требуют отдельного нагрузочного и security-аудита до использования для хранения записей.

### 2.4. Архитектурное решение

Существующий Go backend остаётся единственной внешней точкой API и отвечает за права, школы, задания, попытки и результаты. ML-обработка выносится в отдельный Python-сервис. Аудиофайлы хранятся в S3-совместимом объектном хранилище. Обработка выполняется асинхронно.

## 3. Границы MVP

### 3.1. В MVP входит

- создание преподавателем задания на чтение выбранной суры и диапазона аятов;
- просмотр задания учеником;
- запись или загрузка аудио продолжительностью до 60 секунд;
- проверка формата, размера и длительности записи;
- асинхронная обработка;
- распознавание/декодирование коранической речи;
- сопоставление результата с известным эталоном;
- обнаружение пропуска, замены, повтора и лишнего слова;
- оценка уверенности;
- визуальное объяснение результата;
- подтверждение и исправление ошибок преподавателем;
- повторная попытка ученика;
- история попыток и базовая динамика;
- выгрузка обезличенных результатов эксперимента.

### 3.2. В MVP не входит

- автоматическая итоговая религиозная оценка чтения;
- полная проверка всех правил таджвида;
- голосовая идентификация человека;
- генерация или клонирование голоса;
- постоянное прослушивание микрофона;
- распознавание произвольной длинной суры в реальном времени;
- автоматическая публикация результата родителю без подтверждения преподавателя;
- обучение модели на пользовательских записях без отдельного согласия.

## 4. Пользовательские роли и сценарии

### 4.1. Преподаватель или назначенный сотрудник

1. Открывает урок или группу.
2. Создаёт задание на чтение.
3. Выбирает суру, начальный и конечный аят, срок и допустимое число попыток.
4. Получает список отправленных попыток.
5. Видит аудиоплеер, эталонный текст и предполагаемые ошибки.
6. Подтверждает, удаляет или изменяет каждую ошибку.
7. Добавляет комментарий и публикует результат ученику.

### 4.2. Ученик

1. Открывает назначенное задание.
2. Даёт браузеру разрешение на микрофон.
3. Записывает чтение и прослушивает запись локально.
4. Явно отправляет выбранную запись.
5. Видит статус обработки.
6. После проверки преподавателем получает результат и может выполнить следующую попытку.

### 4.3. Родитель

В первой версии видит только опубликованный преподавателем итог и динамику. Исходное аудио и неподтверждённые предположения модели по умолчанию недоступны.

## 5. Целевая архитектура

```text
React/Vite
   │ HTTPS/JWT
   ▼
Go API (Gin)
   ├── PostgreSQL: задания, попытки, ошибки, проверки, метрики
   ├── S3/MinIO: исходное и нормализованное аудио
   └── очередь заданий
            │
            ▼
Python AI Worker/API
   ├── FFmpeg: проверка и нормализация аудио
   ├── ASR/CTC модель
   ├── нормализатор арабского текста
   ├── алгоритм выравнивания
   └── расчёт ошибок и уверенности
```

### 5.1. Ответственность Go backend

- аутентификация и авторизация;
- проверка принадлежности сущностей одной школе;
- выдача временной ссылки для загрузки или приём multipart-файла в MVP;
- создание попытки и постановка задания на обработку;
- хранение статусов;
- выдача результата пользователю;
- аудит действий преподавателя;
- обеспечение идемпотентности API.

### 5.2. Ответственность Python-сервиса

- безопасное чтение входного аудио;
- преобразование в mono PCM 16 kHz;
- VAD/удаление лишней тишины без изменения содержательной речи;
- выполнение инференса;
- нормализация и выравнивание;
- формирование структурированного результата;
- запись технических метрик и версии модели;
- отсутствие прямого публичного доступа из интернета.

### 5.3. Очередь задач

Рекомендуемый production-вариант — Redis и отдельный worker. Для исследовательского прототипа допустима очередь в PostgreSQL с выборкой через `FOR UPDATE SKIP LOCKED`. Обработка внутри HTTP-запроса запрещена из-за длительности инференса и текущего серверного тайм-аута.

### 5.4. Хранение аудио

Рекомендуется S3-совместимое хранилище, локально — MinIO. В базе хранятся только ключ объекта, контрольная сумма, формат, размер и длительность. Публичные постоянные URL не создаются.

### 6.3. `recitation_attempts`

- `id UUID PK`;

## 7. API

Префикс: `/api/recitation`.

### 7.1. Задания

- `POST /assignments` — создать черновик;
- `POST /assignments/:id/publish` — опубликовать;
- `GET /assignments?groupId=&status=` — список;
- `GET /assignments/:id` — карточка;
- `PATCH /assignments/:id` — изменить черновик;
- `POST /assignments/:id/close` — закрыть.

Создание доступно `teacher` и `staff` с доступом к группе. Ученик получает только задания своей группы.

### 7.2. Попытки

- `POST /assignments/:id/attempts` — создать попытку и получить параметры загрузки;
- `POST /attempts/:id/audio` — загрузить файл в упрощённом MVP;
- `POST /attempts/:id/submit` — завершить загрузку и поставить задачу;
- `GET /attempts/:id` — статус и разрешённый для роли результат;
- `GET /assignments/:id/attempts` — список для преподавателя;
- `POST /attempts/:id/retry-processing` — технический повтор обработки.

### 7.3. Проверка

- `POST /attempts/:id/reviews` — сохранить проверку;
- `PUT /reviews/:id` — изменить до публикации;
- `POST /reviews/:id/publish` — опубликовать ученику;
- `GET /attempts/:id/audio-url` — короткоживущая ссылка при наличии права.

### 7.4. Внутренний ML API

- `POST /internal/v1/jobs`;
- `GET /internal/v1/jobs/:id`;
- `GET /internal/v1/health`;
- `GET /internal/v1/models/current`.

Внутренние вызовы защищаются сетевой изоляцией и отдельным service credential. Пользовательский JWT не передаётся ML-сервису.

### 7.5. Формат результата анализа

## 8. Алгоритмический контур

### 8.1. Базовый конвейер

1. Проверить контейнер и реальный media type.
2. Ограничить размер и длительность.
3. Декодировать аудио изолированным процессом FFmpeg.
4. Привести к mono 16 kHz PCM.
5. Определить речевые интервалы.
6. Получить гипотезу ASR либо фонемный CTC-вывод.
7. Нормализовать эталон и гипотезу одной версией алгоритма.
8. Выполнить динамическое выравнивание токенов.
9. Преобразовать операции выравнивания в типы ошибок.
10. Рассчитать WER, уверенность и флаг обязательной проверки.
11. Сохранить результат с версией модели и алгоритмов.

### 8.2. Нормализация арабского текста

Каждое преобразование должно быть конфигурируемым и версионированным. Для word-level MVP предполагаются:

- Unicode NFC;
- удаление знаков остановки и служебных символов;
- унификация вариантов алифа только в оценочном представлении;
- настраиваемая обработка огласовок;
- сохранение исходного текста для отображения;
- запрет необратимой подмены канонического текста в хранилище.

### 8.3. Выравнивание

Для первой версии применяется динамическое программирование с весами операций. Поскольку целевой аят известен, декодирование следует ограничивать допустимым диапазоном текста. Повторы должны распознаваться как отдельный тип, а не смешиваться со вставками.

### 8.4. Базовые модели

В исследовательском стенде необходимо сравнить минимум:

1. Whisper-подобную multilingual ASR как быстрый baseline;
2. Quran-specific ASR/CTC модель;
3. фонемную модель на признаках wav2vec2/XLS-R при доступности совместимых весов и лицензии.

Выбор производится не по популярности модели, а по WER и F1 ошибок на закрытом наборе телефонных записей пилотной школы.

### 8.5. Защита от «угадывания» аята

Обычная ASR может восстановить правильный знакомый текст и скрыть фактическую ошибку. Поэтому необходимо:

- хранить сырой вывод и оценки токенов;
- сравнивать unconstrained и constrained decode;
- помечать низкую уверенность;
- оценивать ошибки на специально записанных неправильных чтениях;
- постепенно переходить к фонемному выводу;
- не обучать и не тестировать на одних и тех же голосах/записях.

## 9. Требования к frontend

### 9.1. Компонент записи

- использовать `MediaRecorder` с проверкой поддержки формата;
- показывать таймер и состояние микрофона;
- ограничить запись 60 секундами;
- позволить прослушать запись до отправки;
- отправлять данные только после явного нажатия пользователя;
- корректно обрабатывать запрет доступа к микрофону;
- не сохранять запись в `localStorage`;
- обеспечить работу на актуальных мобильных Chrome и Safari.

### 9.2. Экран результата

- канонический арабский текст остаётся неизменным;
- ошибки показываются визуальным слоем поверх токенов;
- для каждой ошибки отображаются тип и уверенность;
- низкая уверенность явно обозначается;
- до публикации показывается маркировка «Предварительный анализ ИИ»;
- преподаватель может подтвердить, удалить или заменить ошибку;
- ученик видит только опубликованный результат.

### 9.3. Точка интеграции

В `LessonPage` добавляется блок задания на чтение, в `StudentHomePage` — карточка назначенного задания, в `QuranPage` — действие «Практиковать чтение» для выбранного диапазона. Рекомендуется создать отдельные страницы, а не перегружать существующий читатель Корана.

## 10. Безопасность и персональные данные

- голосовые записи детей обрабатываются только при наличии правового основания и согласия законного представителя;
- согласие на использование записи для проверки и согласие на обучение модели должны быть раздельными;
- по умолчанию запись используется только для оказания функции и не попадает в обучающий датасет;
- перед каждым доступом проверяются `school_id`, группа, студент и роль;
- объектные ключи нельзя принимать от клиента как доверенные;
- ссылки на аудио имеют короткий TTL;
- шифрование трафика обязательно;
- production secrets не хранятся в Git;
- логирование не должно содержать JWT, пароли, полный текст персональных комментариев или URL с доступом к аудио;
- должны быть предусмотрены сроки хранения и удаление по запросу;
- dataset export выполняется только после обезличивания и проверки согласия;
- загружаемый файл проверяется по сигнатуре, размеру и фактической длительности;
- FFmpeg запускается с ограничениями CPU, памяти и времени;
- необходимы rate limits на создание попыток и загрузку аудио.

Рекомендуемый срок хранения исходного аудио пилота — 90 дней, если школа и согласие не требуют более короткого срока. Агрегированные метрики и человеческая разметка могут храниться отдельно в обезличенном виде.

## 11. Нефункциональные требования

### 11.1. Производительность

- запись до 60 секунд и 15 МБ;
- ответ API о принятии загрузки — до 2 секунд без учёта передачи файла;
- медианная обработка — до 15 секунд на целевой GPU;
- 95-й перцентиль — до 45 секунд;
- пользователь видит обновление статуса без перезагрузки страницы.

### 11.2. Надёжность

- идемпотентная отправка попытки;
- повтор задачи после временной ошибки;
- после исчерпания попыток — состояние `failed`, а не бесконечная обработка;
- контрольная сумма файла;
- миграции имеют корректный `down` и тестируются на чистой базе;
- результат всегда содержит версию модели и нормализатора.

### 11.3. Наблюдаемость

Метрики:

- длина очереди;
- время ожидания и обработки;
- доля ошибок декодирования;
- доля ручных исправлений;
- WER и F1 по версии модели;
- использование GPU/CPU и памяти;
- число попыток по школе без раскрытия персональных данных.

### 11.4. Совместимость

- desktop/mobile Chrome последних двух основных версий;
- Safari iOS последних двух основных версий;
- адаптивный интерфейс от ширины 360 px;
- backend API сохраняет совместимость с действующим журналом.

## 12. Эксперимент и методика оценки

### 12.1. Выборка

- 20–30 участников;
- минимум 100 валидных записей;
- несколько моделей телефонов;
- правильное чтение и естественные ошибки;
- четыре заранее зафиксированные короткие суры;
- отдельная закрытая тестовая часть, не используемая для настройки.

### 12.2. Разметка

- преподаватель размечает запись до просмотра результата модели;
- минимум 20% контрольных записей размечаются вторым экспертом;
- разногласия фиксируются, а не автоматически затираются;
- инструкция разметчику описывает типы ошибок и спорные случаи;
- пауза на дыхание сама по себе не является пропуском.

### 12.3. Метрики модели

- WER;
- precision, recall и F1 по всем ошибкам;
- F1 отдельно по пропускам, заменам и повторам;
- точность локализации токена;
- false positive rate на правильном чтении;
- доля результатов ниже порога уверенности.

### 12.4. Продуктовые метрики

- медианное время проверки преподавателем без подсказки;
- медианное время проверки с подсказкой;
- доля принятых без исправления ошибок модели;
- доля завершённых учеником заданий;
- количество повторных попыток;
- оценка полезности преподавателем по анкете.

### 12.5. Целевые значения MVP

- F1 основных ошибок ≥ 0,80;
- false positive rate на правильном чтении ≤ 0,15;
- локализация ошибки ≥ 80%;
- сокращение времени проверки ≥ 40%;
- успешная обработка валидных файлов ≥ 95%;
- ни один неподтверждённый результат не публикуется как окончательный.

## 13. План реализации

### Этап 0. Заявка и фиксация гипотезы — 2–4 сентября

- согласовать проблему с пилотной школой;
- определить одного ответственного преподавателя;
- утвердить четыре суры и типы ошибок;
- получить письмо о готовности участвовать в пилоте;
- сдать одностраничную технологическую гипотезу;
- зафиксировать доступное GPU и production-инфраструктуру.

Результат: согласованная гипотеза, пилотная площадка и критерии успеха.

### Этап 1. Исследовательский baseline — 5–14 сентября

- закрепить канонический текст и его версию;
- создать набор тестовых эталонных и ошибочных записей;
- реализовать CLI: файл + сура/аят → гипотеза + diff;
- сравнить не менее двух моделей;
- измерить WER, время и основные ошибки;
- сформировать первый отчёт.

Результат: воспроизводимый локальный технологический прототип без интеграции в сайт.

### Этап 2. Интерфейс и запись — до 1 октября

- добавить задания на чтение;
- добавить запись/предпрослушивание/отправку;
- добавить таблицы попыток;
- развернуть MinIO/S3;
- добавить статусы обработки;
- интегрировать baseline-модель.

Результат: end-to-end демонстрация на одном тестовом пользователе.

### Этап 3. Собственный алгоритм — до 30 октября

- версионированная нормализация;
- constrained alignment;
- классификация четырёх типов ошибок;
- оценка уверенности;
- экран экспертной проверки;
- реестр версий модели;
- автоматические тесты нормализатора, alignment и прав доступа.

Результат: Level 3 Tech Product — собственный алгоритм и измеримая метрика.

### Этап 4. Пилот — до 30 ноября

- оформить согласия;
- собрать не менее 100 записей;
- провести слепую экспертную разметку;
- измерить технические и продуктовые метрики;
- описать ограничения;
- подготовить демонстрацию и итоговый отчёт.

Результат: Level 4 Deep Tech — эксперимент с партнёром.

### Этап 5. После пилота

- перейти к фонемной модели;
- исследовать отдельные правила таджвида;
- расширить датасет;
- формировать персональные упражнения;
- провести коммерческий и лицензионный аудит внешних моделей и данных.

## 14. Приоритетный backlog

### P0 — обязательно для технологического MVP

### P1 — желательно для пилота

- экспорт обезличенного эксперимента;
- dashboard метрик;

### P2 — после подтверждения гипотезы

## 15. Стратегия тестирования

### Backend

- unit-тесты нормализации входа и business rules;
- repository-тесты с PostgreSQL;
- проверки межшкольной изоляции;
- проверки ролей `teacher/staff/student/parent`;
- идемпотентность submit;
- ошибочные форматы и превышение лимитов.

### ML

- golden-набор известных пар «эталон → гипотеза → ошибки»;
- отдельные правильные и ошибочные чтения;
- regression suite по версиям модели;
- тестирование шума, тишины, обрезанного и повреждённого аудио;
- запрет утечки записей между train и test.

### Frontend

- запись, остановка, повтор и отмена;
- отказ в разрешении микрофона;
- мобильные размеры;
- медленная загрузка и обрыв сети;
- отображение RTL-текста;
- запрет ученику видеть чужую попытку;
- запрет публикации непроверенного результата.

## 16. Критерии приёмки MVP

MVP считается принятым, если:

1. преподаватель назначает чтение одного или нескольких аятов;
2. ученик записывает и отправляет аудио с телефона;
3. запрос быстро возвращает статус, а обработка идёт асинхронно;
4. результат содержит эталон, гипотезу, типы ошибок, уверенность и версию модели;
5. преподаватель может исправить результат и опубликовать его;
6. ученик видит только опубликованный результат;
7. данные другой школы недоступны при подмене идентификаторов;
8. невалидное аудио безопасно отклоняется;
9. технические метрики эксперимента экспортируются без персональных данных;
10. на закрытой пилотной выборке достигнуты либо честно измерены целевые показатели;
11. документированы ограничения и случаи, когда система требует ручной проверки.

## 17. Команда и зоны ответственности

Минимальный состав:

- product/backend разработчик — Go API, данные, интеграция и развёртывание;
- ML разработчик — baseline, модели, выравнивание и оценка;
- frontend разработчик — запись, задания и проверка;
- преподаватель-эксперт — разметка и методика;
- представитель пилотной школы — организация эксперимента и согласия.

Для небольшой команды роли разработчиков могут совмещаться, но роль преподавателя-эксперта нельзя заменять автоматической моделью.

## 18. Что необходимо решить до начала разработки

1. Точная модель GPU, объём VRAM, RAM и диска.
2. Какая школа участвует в пилоте и кто эксперт.
3. Есть ли несовершеннолетние участники.
4. Где будет храниться аудио и допустим ли MinIO на собственном сервере.
5. Какой канонический источник текста используется и какая риваят фиксируется.
6. Какие четыре суры и типы ошибок входят в MVP.
7. Разрешено ли хранить аудио после публикации результата и сколько дней.
8. Какие внешние датасеты и веса допустимы для будущего коммерческого применения.

## 19. Первый практический шаг

Не начинать с изменения сайта. Сначала создать изолированный исследовательский прототип `research/recitation-baseline`, который принимает локальный аудиофайл и идентификатор аята, запускает две модели, нормализует результат и формирует JSON с выравниванием. После измерения на 20–30 собственных тестовых записях выбрать модель и только затем проектировать production-интеграцию.
